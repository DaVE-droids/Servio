# Servio Changelog

A running, human-readable record of *why* changes were made — not just what changed (git history and diffs already cover that), but the reasoning behind it: which spec section it implements, a decision made mid-build, a deviation from the original docs, or a bug it fixed. Entries cover both frontend/app code and backend/db changes (Firestore rules, indexes, Storage rules, data model).

New entries are appended as work happens, not backfilled after the fact.

**Decision (no code change):** Firebase project remains on the Spark (free) plan; no backend migration.
**Why:** User's Firebase billing balance was removed and the project was downgraded to Spark. Every feature built and every phase in the roadmap runs entirely client-side against Firestore/Auth/Storage/FCM, all within Spark's free quota — the SAD's ADR-005 deliberately avoided Cloud Functions for the MVP, so nothing planned requires Blaze. Migrating to a different backend now would mean redoing the already-complete Authentication/Profile/Internship work for a cost problem that isn't being hit yet.
**Follow-up:** Revisit only if Firestore daily read/write quotas are genuinely being approached, or if a later phase (most likely Phase 6, notification fan-out) needs a Blaze-only feature — in which case re-enable Blaze with a budget alert configured first.

- Added `rejectedAt` field to `InternshipModel` (`lib/features/internship/data/models/internship_model.dart`), mirroring `approvedAt`.
- Added `rejectInternship()` to `InternshipService` and `InternshipRepository` (`lib/features/internship/data/services/internship_service.dart`, `.../repositories/internship_repository.dart`), mirroring the existing `approveInternship()` pattern.
- Changed `PendingInternshipsController.approve()` to return `Result<void>` instead of swallowing it (it previously discarded the repository's result despite a comment claiming "the UI layer will handle showing that error" — that was never actually possible with a `void` return). Added a matching `reject()` method.
- Added `lib/features/coordinator/presentation/screens/coordinator_dashboard_screen.dart` — lists pending placements as cards (company, department/state, student ID, submitted date) with Approve/Reject actions; Reject requires confirmation via `AppDialog` per the DSS's Dialog Standards (§20: "Reject internship?" is listed as a use case requiring confirmation). Wired at `/coordinator/dashboard` in `app_router.dart`, replacing the placeholder for the `coordinator` role only.
- **Backend/db:** extended `firestore.rules` — added `rejectedAt` to `internshipFields()`, added `isValidCoordinatorRejection()` (mirrors `isValidCoordinatorApproval()`, only allows the `pending_review → rejected` transition), and the `internships` update rule now allows either approval or rejection. Added a composite index to `firestore.indexes.json` (`status` ASC + `submittedAt` ASC) — required because `getPendingInternships()` filters on `status` and orders by a different field (`submittedAt`), which Firestore cannot serve from automatic single-field indexes alone.
- Also tightened the generic `permission-denied` error message in `InternshipRepository` (was hardcoded to "...submit this placement," which would have shown on a denied approve/reject too) to a role-neutral message, since the same mapper is now shared by three different actions.

Adding `rejected` to the enum is a deliberate deviation from the DDS's literal status list (`draft, pending_review, approved, assigned, active, completed, archived`), which appears to have simply omitted it.

**Follow-up:**
- The reject action has no reason/comment field — the ARS's `rejectInternship()` signature doesn't specify one, so this stayed minimal for Phase 0. Worth reconsidering once real coordinators are using it.
- No screen yet lets a student see or act on a rejected placement beyond the dashboard showing "Rejected" in red — resubmission after rejection isn't built.
- Card shows the student's `studentId`, not their name — `internships` documents don't denormalize `studentName` (only `attendance`/`logbook_entries`/`supervision_reports` do, per the DDS), and adding a live lookup was out of scope for a "quick win" phase.

**Changed (app code, bug fixes found during hands-on testing):** Two issues surfaced while testing Phase 0/1 in the simulator, both fixed.
1. **Internship submission was effectively unusable** — `StudentInternshipScreen` required manually typing raw company latitude/longitude decimal values, which a real user has no way to know (confirmed broken even after looking up real coordinates). Removed the Latitude/Longitude fields, their `AppTextField`s, `TextEditingController`s, and the review-screen "Coordinates" row entirely from `student_internship_screen.dart`; removed the now-dead `InternshipValidator.latitude()`/`longitude()` methods and their tests. Submission now sends a placeholder `(0.0, 0.0)` for `companyLatitude`/`companyLongitude`, with a code comment pointing at the roadmap's new "Known gap — company location capture" section, which documents the real fix (Maps picker or geocoding) as a prerequisite for Phase 5 (Supervision's "Navigate to company" feature needs real coordinates to mean anything).
2. **Pixel overflow on the student dashboard** — `_DashboardGrid` used `GridView.count` with a `childAspectRatio` that computed a card height too short for its content once a card's action button was showing (confirmed by hand: icon/title row + value + 2-line description + button routinely exceeded the ~110–130px the old ratio produced). Switched to `GridView.builder` with `SliverGridDelegateWithFixedCrossAxisCount(mainAxisExtent: 210)` — a fixed, directly-reasoned-about pixel height instead of fragile width-derived ratio math — and capped `StudentDashboardSummaryCard`'s description to `maxLines: 2` with `TextOverflow.ellipsis` as a second line of defense so it can't overflow regardless of text length or system font scaling.

**Why:** User hit both while manually testing the app in the iOS Simulator before agreeing to commit anything — testing before committing surfaced two real defects that automated tests (which don't touch actual layout/UX) hadn't caught.

**Follow-up:** Company location capture is now explicitly tracked in the roadmap as a gap to close before Phase 5. No Google Maps Platform API key is provisioned anywhere in this project yet — needed before that work can start.

**Changed (app code, bug fix found during hands-on testing):** Approving a placement in the "Pending Review" tab didn't make it show up in "Needs Lecturer" without a manual pull-to-refresh.
**Why:** `PendingReviewTab` and `NeedsLecturerTab` are backed by two independent providers (`pendingInternshipsProvider`, `approvedInternshipsProvider`), each fetched once when the dashboard screen builds. `PendingInternshipsController.approve()` only called `ref.invalidateSelf()`, refreshing its own list but leaving the other tab's already-fetched data stale — it had no way to know a placement it hadn't seen yet had just become eligible for it. Fixed by also calling `ref.invalidate(approvedInternshipsProvider)` on a successful approve, in `lib/features/coordinator/presentation/providers/pending_internships_provider.dart`.
**Follow-up:** None — `reject()` doesn't need the same fix since a rejected placement never enters the approved bucket. If a third bucket/tab is added later (e.g. "Assigned"), the same cross-invalidation pattern will need repeating for it.

**Added (dev tooling, backend/db data — not app code):** `scripts/seed_test_users.js` — a one-off Node.js script using the Firebase Admin SDK to create test lecturer and student accounts directly in the live `servio-e2974` project.
**Why:** Testing Phase 1 (lecturer assignment) needs at least one account with the lecturer role to appear in the assignment dropdown, and none existed. The Firestore rules deliberately only allow client-side self-registration with `role == 'student'` (`isValidStudentProfileCreate` in `firestore.rules`) — there's no app-side signup flow for lecturer or coordinator accounts at all, by design (matches ARS: "Role is assigned at registration and cannot be changed by the user"). So seeding those roles requires admin-level access that bypasses security rules entirely, which only the Firebase Admin SDK (authenticated via a service account key, not the app's normal client SDK) can do.
Created 3 lecturers and 3 additional students (all `users` fields DDS-documented as required or optional filled in, `isEmailVerified`/`isActive` set true so they can log in immediately without the verification-email step). Credentials: one shared password for all seeded accounts (kept in the gitignored `scripts/seed-output.json`, never in git); emails follow `lecturer.<lastname>@servio.test` / `student.<lastname>@servio.test`.
**Follow-up:** The service account key (`scripts/servio-account.json`), `scripts/node_modules/`, and `scripts/seed-output.json` (the generated credential list) are all gitignored — never commit any of them. The script itself and `scripts/package.json` are safe to commit (no secrets, just seed data). This script talks to the **live** project, not an emulator — rerunning it is safe (upserts by email, won't duplicate), but be deliberate about running it against production-like data later.

**Fixed (app code, navigation architecture — found during hands-on testing):** User reported the student dashboard's bottom-nav tabs animated like screens were "stacking," and that entering the lecturer's Assigned Students screen had no way back. Audited every navigation call in the app (`grep -rn "context\.go(\|context\.push("`) and found **`context.push()` was never used anywhere** — every internal navigation, including genuine drill-down screens, used `context.go()`. This is two distinct bugs, not one:
1. **Wrong transition on tab switches**: the 5 student bottom-nav destinations (`studentDashboard`, `attendance`, `logbook`, `notifications`, `profile`) are each separate top-level `GoRoute`s; switching between them via `.go()` triggered Flutter's default slide-transition page animation every time, which reads as screens stacking rather than an instant tab switch. Fixed by giving these 5 routes a `pageBuilder` returning `NoTransitionPage` in `lib/app/router/app_router.dart`, instead of the default `builder`. `/profile` specifically needed a role-conditional split — `NoTransitionPage` for the student-tab branch, `MaterialPage` (default transition preserved) for the lecturer/coordinator branch, since the same path serves both a tab switch and a genuine push depending on role.
2. **Missing back button on drill-down screens**: `.go()` replaces the whole navigation stack rather than pushing onto it, so screens reached via `.go()` that *aren't* tabs (Internship submission from the student dashboard, Assigned Students and Profile from the lecturer dashboard) had nothing left in the stack to return to. Changed these three call sites to `context.push(...)`: `student_dashboard_screen.dart` (both "Submit"/"View" internship actions) and `lecturer_dashboard_screen.dart` ("View Students", "Open Profile"). Confirmed the destination screens already render inside their own `Scaffold`/`AppBar` (`LecturerAssignedStudentsScreen`, `ProfileScreen(showScaffold: true)`), so the back button appears automatically — no manual back-button code needed, Flutter provides it once there's something to pop.

While auditing, also found the **coordinator had no way to reach their own Profile screen at all** — no button anywhere linked to it. Added a profile icon button to `CoordinatorDashboardScreen`'s app bar using `context.push()`, same pattern as the lecturer dashboard.

**Why:** User explicitly asked to audit every screen in the codebase for this pattern before continuing with any other work, since it's foundational to how the whole app feels — not something to patch piecemeal per-screen later. `.go()` vs `.push()` is a real distinction in `go_router`: `.go()` means "this is where the user is now" (correct for tab switches and post-action landings), `.push()` means "the user drilled into this, and should be able to back out" (correct for detail/action screens). The bug was using `.go()` uniformly regardless of which one applied.

**Follow-up:** Not a memory leak — verified `.go()` does properly dispose the replaced route's widget tree, and Riverpod's app-level providers aren't duplicated by navigation (they're not tied to widget lifecycle). The reported symptom was a wrong transition + missing back-stack entries, both now fixed, not unbounded state growth. If a future phase adds real sub-navigation within a tab (e.g., a notification opening a detail view while staying "in" the Notifications tab), reconsider `StatefulShellRoute.indexedStack` for a fully independent per-tab navigation stack — not needed today since no tab currently has its own internal drill-down.
