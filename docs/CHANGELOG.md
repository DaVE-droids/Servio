**Fixed (app code, navigation architecture — found during hands-on testing):** User reported the student dashboard's bottom-nav tabs animated like screens were "stacking," and that entering the lecturer's Assigned Students screen had no way back. Audited every navigation call in the app (`grep -rn "context\.go(\|context\.push("`) and found **`context.push()` was never used anywhere** — every internal navigation, including genuine drill-down screens, used `context.go()`. This is two distinct bugs, not one:
1. **Wrong transition on tab switches**: the 5 student bottom-nav destinations (`studentDashboard`, `attendance`, `logbook`, `notifications`, `profile`) are each separate top-level `GoRoute`s; switching between them via `.go()` triggered Flutter's default slide-transition page animation every time, which reads as screens stacking rather than an instant tab switch. Fixed by giving these 5 routes a `pageBuilder` returning `NoTransitionPage` in `lib/app/router/app_router.dart`, instead of the default `builder`. `/profile` specifically needed a role-conditional split — `NoTransitionPage` for the student-tab branch, `MaterialPage` (default transition preserved) for the lecturer/coordinator branch, since the same path serves both a tab switch and a genuine push depending on role.
2. **Missing back button on drill-down screens**: `.go()` replaces the whole navigation stack rather than pushing onto it, so screens reached via `.go()` that *aren't* tabs (Internship submission from the student dashboard, Assigned Students and Profile from the lecturer dashboard) had nothing left in the stack to return to. Changed these three call sites to `context.push(...)`: `student_dashboard_screen.dart` (both "Submit"/"View" internship actions) and `lecturer_dashboard_screen.dart` ("View Students", "Open Profile"). Confirmed the destination screens already render inside their own `Scaffold`/`AppBar` (`LecturerAssignedStudentsScreen`, `ProfileScreen(showScaffold: true)`), so the back button appears automatically — no manual back-button code needed, Flutter provides it once there's something to pop.

While auditing, also found the **coordinator had no way to reach their own Profile screen at all** — no button anywhere linked to it. Added a profile icon button to `CoordinatorDashboardScreen`'s app bar using `context.push()`, same pattern as the lecturer dashboard.

**Why:** User explicitly asked to audit every screen in the codebase for this pattern before continuing with any other work, since it's foundational to how the whole app feels — not something to patch piecemeal per-screen later. `.go()` vs `.push()` is a real distinction in `go_router`: `.go()` means "this is where the user is now" (correct for tab switches and post-action landings), `.push()` means "the user drilled into this, and should be able to back out" (correct for detail/action screens). The bug was using `.go()` uniformly regardless of which one applied.

**Follow-up:** Not a memory leak — verified `.go()` does properly dispose the replaced route's widget tree, and Riverpod's app-level providers aren't duplicated by navigation (they're not tied to widget lifecycle). The reported symptom was a wrong transition + missing back-stack entries, both now fixed, not unbounded state growth. If a future phase adds real sub-navigation within a tab (e.g., a notification opening a detail view while staying "in" the Notifications tab), reconsider `StatefulShellRoute.indexedStack` for a fully independent per-tab navigation stack — not needed today since no tab currently has its own internal drill-down.

**Changed (app code + backend/db):** Phase 3 — Attendance. Students can check in/out daily; lecturers can see attendance across their assigned students.
- Built out `lib/features/attendance/` end to end (model, service, repository, 4 use cases, controller/state, providers) — previously pure placeholder stubs.
- **`AttendanceStatus` didn't serialize to the DDS's snake_case convention** (unlike `InternshipStatus`) — `checkedIn`/`completed`/etc. were being written to Firestore as raw Dart enum names instead of `checked_in`/`completed`/etc. Added the same `firestoreValue`/`label`/`fromFirestore` extension pattern already used for `InternshipStatus`, fixing the inconsistency while building this.
- **Duplicate check-in prevention uses a deterministic document ID** (`{internshipId}_{yyyy-MM-dd}`), not an auto-ID — a deliberate deviation from DDS §27.3 ("use auto IDs everywhere except `users`"). Reasoning: ARS §9 explicitly requires a transaction for check-in to prevent two concurrent check-ins both succeeding, but Firestore transactions can only `transaction.get()` a *known document path* — they can't run a query as the read step. A deterministic ID is the standard, correct Firestore pattern for "one document per natural key," and it's what makes the transaction actually enforceable. `AttendanceService.checkIn()` reads that exact doc inside a transaction and only creates it if absent.
- **No GPS/location capture** — `checkInLatitude`/`checkInLongitude`/etc. exist as nullable fields on `AttendanceModel` (matching the DDS schema) but are never populated. The DDS marks them optional, and this project has no `geolocator` dependency, no `NSLocationWhenInUseUsageDescription` in `Info.plist`, and no Android location permissions configured — building real GPS capture (with the NFR-PRIV-required "explain why before requesting" UX) is its own scope, deferred as a clear follow-up rather than bolted on here.
- **`lecturerName` denormalized onto `internships`** (not just attendance/logbook/supervision as the DDS's denormalization table specifies) — a student cannot read their lecturer's `users` profile under current rules, and broadening that felt like a bigger, murkier permission change than having the coordinator (who already has the lecturer's name in hand when picking them from the dropdown) write it once at assignment time. `InternshipRepository.assignLecturer()` now takes `lecturerName` alongside `lecturerId`; `AssignLecturerDialog` returns the full `UserModel` instead of just a UID so the caller has the name to pass through.
- **Found and fixed a real blocker while building this**: nothing in the app moved an internship from `assigned` to `active`, and DDS gates attendance entirely on `active` status — meaning Attendance would have been permanently unreachable for any real placement. Added a minimal "Activate" step, mirroring the approve/reject/assign pattern exactly: `activateInternship()` on the repository/service, a new `activatedAt` field on `InternshipModel` (also not in the DDS's literal field list — same gap as the missing `rejected` status found in Phase 0), a third Coordinator dashboard tab ("Ready to Start") listing `assigned` placements with an Activate button, and `isValidCoordinatorActivation()` in the rules.
- New screens: `StudentAttendanceScreen` (today's check-in/check-out card + history list, wired at `/attendance` for students — replacing `StudentComingSoonScreen`) and `LecturerAttendanceScreen` (recent attendance across assigned students, pushed from the lecturer dashboard). `/attendance` needed the same role-conditional `NoTransitionPage`/`MaterialPage` split as `/profile` from the navigation fix above, since it's a tab for students but a genuine push target for lecturers.
- **Backend/db:** new `attendance` collection rules (`isValidAttendanceCreate()` validates the internship is active and owned by the requesting student; `isValidAttendanceCheckOut()` only allows the specific checked_in → completed transition) and `isValidCoordinatorActivation()`. Two new composite indexes (`attendance`: `internshipId+date`, `lecturerId+date`) plus dry-run validated and deployed, same as every prior phase.

**Why:** This was Phase 3 of the roadmap. The activation-step and lecturerName-denormalization decisions weren't explicitly scoped in the roadmap's one-line Phase 3 description — both were discovered as hard blockers/prerequisites while implementing against the DDS's actual stated business rules, not scope creep for its own sake.

**Follow-up:**
- GPS/location capture for check-in/check-out (see above) — needs a `geolocator` dependency, platform permission config, and a proper NFR-PRIV-003-compliant "why we're asking" UX before requesting.
- No per-student attendance detail view for lecturers yet (just a flat recent-records list) — matches the same "minimum viable" scope call made for Assigned Students in Phase 2.
- `getAttendanceStatistics()` from the ARS's repository spec wasn't built — the roadmap's Phase 3 description only called for check-in/check-out/today/history, not statistics.

Accepted as a reasonable MVP trade-off (documented, not silent) — enforcing it fully in rules would require timestamp-to-date-string formatting Firestore's rules language doesn't have good support for.

**Fixed (app code + backend/db, found while hands-on testing Phase 3 myself in the Simulator):** Three real bugs in the check-in/check-out flow, none caught by `flutter analyze`/tests since they only surface against live Firestore rules and data.
1. **Check-in hard-blocked on a data-migration gap.** The test internship had `lecturerId` set but `lecturerName` null (it was assigned before this phase added that field). `AttendanceController.checkIn()` required both, so check-in failed outright over a missing *display* field. Loosened the guard to only require `lecturerId`, falling back to the ID string for `lecturerName` when the denormalized name is missing (`internship.lecturerName ?? internship.lecturerId!`) — same degrade-gracefully approach used for "Student ID, not name" elsewhere, not a new pattern.
2. **`getTodayAttendance()` failed with `permission-denied` on the very first check of any day.** The rule dereferenced `resource.data.studentId`, but `resource` is `null` for a document that doesn't exist yet (which is exactly the common case — before any check-in, today's deterministic doc doesn't exist). Firestore treats that dereference-on-null as a rule *evaluation error*, and treats evaluation errors as denials, not a clean not-found. Fixed with a `!exists(...)` branch so a lookup on a missing doc resolves to not-found instead of erroring.
3. **`getAttendanceHistory()` returned silently empty, no error, even with a matching record confirmed present via direct Admin SDK query.** Root cause was two-layered: (a) the query filtered on `internshipId` while the rule checked `resource.data.studentId` — Firestore's `list` rule needs to *statically prove* every possible result satisfies the rule using only the query's own filter fields, and can't do that across mismatched fields, so switching the query to filter on `studentId` (matching the rule, and matching the DDS's own recommended `attendance: studentId + date` index that had been skipped earlier) was the real fix; (b) after that fix, results were *still* silently empty until `get` and `list` were split into separate `allow` rules — combining the `!exists(...)` branch from fix #2 into the same rule as `list` caused Firestore to silently exclude otherwise-matching documents rather than erroring, for reasons not fully diagnosed (only worked around, not root-caused to the rules-engine's internals). Also worth naming honestly: several retest cycles in between these fixes showed the *same* stale empty result even after rules were corrected, because `AttendanceController` is a plain (non-autoDispose) `AsyncNotifier` that doesn't refetch just from navigating back to its tab — a full app restart was required each time to confirm whether a fix actually worked, which cost real time and should be remembered when debugging this controller in the future.
4. **Dashboard's "Today's Attendance" summary card was still hardcoded placeholder text** ("...will appear here after attendance is implemented") — Phase 3 built the real `/attendance` screen but never wired this card to `attendanceControllerProvider`. Fixed to mirror `_internshipCard`'s live-data pattern exactly (loading/error/not-checked-in/checked-in/completed states, `View` action routing to `/attendance`).
5. **`AttendanceController.build()` used `ref.read(internshipControllerProvider)` instead of `ref.watch(...)`** — a real race condition, not just a style nit. Riverpod doesn't guarantee which of two independent providers' initial async loads resolves first; with `read`, if `AttendanceController.build()` ran before `internshipControllerProvider` had finished loading, it would permanently conclude "no active internship" and never re-check, even after the internship data arrived moments later — reproduced live: the dashboard card showed "Not checked in" for a session that was actually already completed. Fixed by having `build()` `watch` the internship provider directly and pass the resolved internship into `_load(internship)`, while action methods (`checkIn`/`checkOut`) keep using `read` via `_activeInternship()`, since by the time a user can tap those buttons the screen has already rendered with resolved data.

**Why:** Found entirely through hands-on Simulator testing (screenshots + simulated taps), not code review — none of these were visible from reading the code, since they only manifest against real Firestore rule evaluation, real data state, or genuine async timing.

**Follow-up:** The exact mechanism behind fix #3(b) — why combining `!exists()` with data-driven OR-branches in one `list` rule silently drops results instead of erroring — isn't fully understood, just empirically worked around by splitting `get`/`list`. Worth deeper investigation if a similar "exists-check fallback" pattern is needed for another collection's `list` rule later (attendance, logbook, supervision will likely all want the same "check today's deterministic doc" pattern).

**Changed (app code + backend/db):** Phase 4 — Digital Logbook. Students submit daily entries against their active internship; lecturers review with approve/request-changes.

Built the same way as Attendance, deliberately applying every lesson from that phase's five bugs up front rather than rediscovering them:
- `LogbookStatus` got the `firestoreValue`/`label`/`fromFirestore` serialization extension immediately (was missing, same gap `AttendanceStatus` had).
- Deterministic doc ID (`{internshipId}_{yyyy-MM-dd}`) for the same "one entry per working day" reasoning as attendance — though unlike check-in, ARS's own transaction matrix doesn't call for a transaction here, so `submitEntry()` does a plain read-then-set rather than `runTransaction`. Firestore still distinguishes create vs. update by whether the doc existed, so a first submission is a `create()` and a same-day resubmission is an `update()` — the rules have separate `isValidLogbookCreate()` and `isValidLogbookStudentEdit()` functions to match, both sharing a `hasValidLogbookContent()` helper.
- `get`/`list` kept separate from the start (attendance fix #3b), and `getStudentEntries()`/`getPendingReviews()` filter on exactly the fields the rules check (`studentId`, and `lecturerId`+`status`) — attendance fix #3a's lesson, applied up front instead of discovered again.
- `LogbookController.build()` watches `internshipControllerProvider` from the first line, not `read()` — attendance fix #5, applied up front.
- Result: clean `flutter analyze` on the first pass, unlike attendance which needed several rounds of fixes discovered only through hands-on testing.

Business rules from DDS/SRS: one entry per day (enforced by the deterministic ID), editable while `pending` or `changes_requested`, locked once `approved` (BR-LOG-003) — `submitEntry()` explicitly refuses to overwrite an approved entry. Lecturer review is two outcomes only (approve / request changes with required comments), matching FR-LOG-003.

New screens: `StudentLogbookScreen` (form pre-fills from today's entry when one exists and isn't locked; shows a read-only approved-entry card instead of a form once locked; history list below) and `LecturerLogbookReviewScreen` (pending-review queue, Request Changes opens a small dialog collecting required comments). Both wired at the existing `/logbook` route with the same role-conditional `NoTransitionPage`/`MaterialPage` split used for `/attendance` and `/profile`.

**Backend/db:** new `logbook_entries` collection rules and two composite indexes (`studentId+date` for student history, `lecturerId+status+date` for the lecturer's pending queue — the latter matching ARS's own `logbook_entries: lecturerId + status` recommendation, extended with `date` since the query also orders by it).

**Why:** This was Phase 4 of the roadmap. Structured explicitly as "apply the Attendance post-mortem" rather than building from scratch, since the two features share the same daily-record shape (DDS's own denormalization table lists the same fields — studentName, studentMatricNumber, lecturerName, companyName, state — for both collections).

**Changed (app code, bug fix found during hands-on testing):** Fixed a text field auto-capitalization bug that corrupted typed input (most seriously, login passwords) on Email fields across Login, Register, and Forgot Password screens.
